# Как ведётся разработка

Документ описывает процесс, а не код. Архитектура — в
[ARCHITECTURE.md](ARCHITECTURE.md), решения — в [DECISIONS.md](DECISIONS.md),
состояние — в [STATUS.md](STATUS.md).

## 1. Роли

| Роль | Кто | Что делает | Артефакт |
|---|---|---|---|
| Оркестратор | Oscar | декомпозиция, делегирование, приёмка, разрешение конфликтов | задача и критерии приёмки |
| Исследователь | Scout | рынок, движки, стек, план с путями и сигнатурами | `output/research/`, `output/plan/` |
| Исполнитель | Ivan | реализация строго по плану, тесты, доказательства | код, тесты, отчёт |
| Критик | Jester | red team, проверка допущений, поиск слабых мест | замечания и вердикт |

Критик не пишет код и не переписывает план; его замечания либо принимаются
оркестратором, либо отклоняются с обоснованием. Исполнитель не спорит с
планом молча: при противоречии он останавливается и присылает gap report.

## 2. Правило: сначала план, потом реализация

1. Для нетривиальной задачи (больше одного файла или новой логики) сначала
   пишется план в `output/plan/`. План содержит цель, границы, файлы, шаги,
   сигнатуры, тесты и команду проверки каждого шага.
2. План — контракт. Исполнитель идёт по шагам по порядку, не добавляет
   функции «заодно» и не меняет имена/пути без согласования.
3. Если план невыполним, противоречив или устарел — стоп и gap report:
   номер шага, что сказано, в чём проблема, доказательство, предложение.
4. После реализации план и отчёт по возможности копируются в
   [planning/](planning/README.md): `output/` в git не входит и пропадёт при
   переносе.
5. Для багов сначала воспроизведение и падающий тест, затем минимальная
   правка; для фич — тест рядом с кодом, а не «потом».

## 3. Гейты

Каждый гейт обязателен перед коммитом, если он относится к изменённым файлам.
«Зелёный» означает нулевой код возврата и отсутствие `failed`.

| Гейт | Команда | Критерий |
|---|---|---|
| Типы | `pnpm -C apps/readest-app exec tsc --noEmit` | rc=0 |
| JS-тесты | `pnpm -C apps/readest-app test:pr:web:unit` | `0 failed` |
| Rust-ядро | `pnpm --filter @readest/readest-app test:tauri` | зелёный; нужен дисплей |
| Только перевод | `cd apps/readest-app/src-tauri && cargo test -p Readest translation_core -- --nocapture` | 8 passed; без `BIREADER_MODEL_PATH` реальные тесты печатают `SKIP` |
| Линт и формат | `pnpm -C apps/readest-app lint`, `pnpm format:check` | rc=0 |
| Smoke web | `scripts/bilireader-run.sh` | библиотека открывается, книга читается, словарь отвечает |
| Smoke desktop | `scripts/bilireader-run.sh --desktop` или `--cef` | окно, EPUB/FB2, попап перевода |
| Ручная приёмка | [manual-test.md](manual-test.md) B1–B17 | все пункты, применимые к платформе |
| Диск | `df -h /` | ≥ 8 ГБ перед релизной сборкой |

Pre-push hook прогоняет тесты. Его нельзя обходить через `--no-verify`: если
хук падает, надо починить причину, а не пропустить проверку. Полный прогон
на эталонном коммите — 15 110 passed, 16 skipped, 0 failed; известное
исключение — 3 теста `plugins/integration.test.ts` с «File format is not
recognized» в этом окружении.

## 4. Git

| Правило | Детали |
|---|---|
| Ветка | `bilireader/main`; `main` — зеркало `upstream/main`, только fast-forward |
| Remote | `origin` = `MariganMarigam/BiliReader`, `upstream` = `readest/readest` |
| Коммиты | атомарные, один смысл на коммит; сообщения в conventional style (`docs:`, `fix:`, `feat:`) |
| Синхронизация | раз в две недели `git fetch upstream && git merge upstream/main`; rebase опубликованной ветки не используется |
| Субмодули | указатели в git, содержимое — нет; после клона `git submodule update --init --recursive` |
| `foliate-js` | сначала коммит и push в `MariganMarigam/foliate-js` (ветка `feat/text-index`), затем обновление указателя в родителе |
| Запрещено коммитить | `output/`, `dist/`, `.opencode/`, `node_modules/`, `target/`, GGUF, keystore, `.env` с секретами |
| Артефакты | только `dist/`, каталог исключён через `.git/info/exclude` |

Указатель сабмодуля на неопубликованный коммит ломает чистый клон: другой
разработчик не сможет получить объект. Поэтому push в репозиторий сабмодуля
всегда предшествует коммиту родителя.

## 5. Диск

Корневой раздел часто занят на 95–99 %. Бюджет:

| Объект | Размер |
|---|---|
| `target/release/` | ~5.8 ГБ |
| `target/debug/` (CEF) | ~4–5 ГБ, до 8 ГБ со старым профилем |
| `~/.cache/tauri-cef/` | ~1.8 ГБ |
| Релизная сборка целиком | ~6 ГБ + кэш CEF |

Правила:

1. Перед релизной сборкой `df -h /`; меньше 8 ГБ — сначала очистка.
2. `scripts/bilireader-clean.sh` — сухой прогон; `--yes` — удаление. Скрипт
   не трогает данные приложения и модель.
3. Собирать бандлы только на чекпоинте, а не после каждого изменения:
   повседневная работа идёт через `scripts/bilireader-run.sh`.
4. Модель и книги лежат в `~/.local/share/bilireader/` и
   `~/.local/share/com.bilireader.app/`; очистка их не удаляет.

## 6. Как продолжить на новой машине

1. Прочитать по порядку: [STATUS.md](STATUS.md) (что готово),
   [ROADMAP.md](ROADMAP.md) (что дальше), [PORTING.md](PORTING.md) (как
   поднять окружение). Затем этот файл и [ARCHITECTURE.md](ARCHITECTURE.md).
2. Клон с сабмодулями и переключение ветки:
   ```sh
   git clone --recurse-submodules https://github.com/MariganMarigam/BiliReader <project>
   cd <project> && git checkout bilireader/main
   ```
3. Выполнить чек-лист [PORTING.md](PORTING.md#8-чек-лист-переноса): Node 24,
   pnpm 11.1.1, `pnpm install --frozen-lockfile`, `setup-vendors`,
   `scripts/bilireader-check-toolchain.sh`.
4. Проверить [PORTING.md](PORTING.md#9-что-проверить-после-переноса): типы,
   тесты, словарь, шрифты, опционально перевод.
5. Модель скачать в Settings → Language → Offline engine или положить GGUF и
   задать `BIREADER_MODELS_DIR`.

`output/` в свежем клоне не будет — это нормально. Планы и исследования,
которые нужно сохранить, теперь лежат в [planning/](planning/README.md).
